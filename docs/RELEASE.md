# Release Guide

This document is the maintainer checklist for publishing ChatGPT Multitask.
Never publish from failing code, and never merge an unverified branch into
`main`.

## Versioning

The project uses Semantic Versioning. Before 1.0, a minor bump indicates
user-visible features or behaviour changes.

1. Update `version` in `package.json`:

   ```bash
   npm version 0.2.0 --no-git-tag-version
   ```

2. Update `CHANGELOG.md` with the release date and a complete change list.
3. Confirm `package-lock.json` contains the same version.

## Pre-release verification

Run locally (or rely on the CI workflow):

```bash
npm ci
npm run typecheck
npm test
npm run pack:win
```

`npm test` must pass every gate: unit, Electron smoke, theme/zoom, tab
indicators, stabilization, Arabic RTL acceptance, RTL stress, and update
pipeline integrity.

## Artifacts

| Platform | Files |
| --- | --- |
| Windows x64 | `ChatGPT-Multitask-Windows-x64-Setup.exe`, `.blockmap`, `latest.yml` |
| macOS arm64 | `ChatGPT-Multitask-macOS-arm64.dmg`, `.zip`, `latest-mac.yml` |
| macOS x64 | `ChatGPT-Multitask-macOS-x64.dmg`, `.zip`, `latest-mac.yml` |
| All | `SHA256SUMS.txt` |

`latest.yml` and `latest-mac.yml` are generated by electron-builder and are
required by `electron-updater`. Verify before publishing:

- `version` equals `package.json`;
- every `url` entry exists in the release;
- `size` equals the artifact size;
- `sha512` equals the Base64 SHA-512 of the artifact.

The WASM and Node-native dependency set does not require extra runtime files.

## Publishing

1. Merge the validated branch into `develop`, then `main`.
2. Create and push a tag that matches the package version:

   ```bash
   git tag v0.2.0
   git push origin v0.2.0
   ```

3. The `Release` workflow (`.github/workflows/release.yml`):
   - validates that the tag matches `package.json`;
   - runs the full test suite on Windows and macOS;
   - builds Windows and macOS with `--publish never`;
   - validates update metadata and referenced files;
   - downloads both artifact sets on one runner, writes a combined
     `SHA256SUMS.txt`, and calls `gh release create` only after both builds
     succeed.
4. Verify the published assets and checksums on the Releases page.

The `CI` workflow is separate and never publishes. It runs on pushes and pull
requests with read-only repository permissions.

## Signing status

- **Windows:** no Authenticode certificate is configured; builds are unsigned
  and may trigger SmartScreen.
- **macOS:** no Apple Developer certificate or notarization credentials are
  available. Builds are unsigned and not notarized, and macOS automatic update
  cannot be validated without a signed build.

Do not fabricate signatures, notarization or an end-to-end updater result. State
the limitation in the release notes.

## Updater verification

A release is only "updater verified" when two packaged versions have been
installed and the older version successfully:

1. detects the newer release;
2. downloads the artifact and passes checksum verification;
3. restarts and installs the newer version.

A local single-version build can validate metadata, checksums and the UI
contract, but not the full cross-version download/install path. Report that
distinction honestly.

## Post-release

- Confirm the updater sees the new `latest.yml` / `latest-mac.yml`.
- Keep the previous installer and checksums until the next release is verified.
- Archive the build evidence outside the repository.
